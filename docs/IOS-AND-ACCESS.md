# iOS и доступ к приложению

Цель продукта — приложение Chika для iOS. Текущий код — веб-прототип на Next.js, который можно открыть в Safari; это ещё не нативное приложение и не сборка для App Store/TestFlight.

## Следующая архитектура

До приглашения реальных сотрудников нужен общий backend: вход по приглашениям, база сотрудников/смен/задач/инцидентов, серверная проверка доступа и журнал изменений. Его API смогут использовать и веб-приложение, и будущий клиент iOS. Способ создания iOS-клиента (SwiftUI или упаковка совместимого веб-клиента) выбирается отдельно; требования к уведомлениям и офлайн-работе важны для этого решения.

## Администратор — только владелец

Административный доступ должен быть закреплён за одним подтверждённым user ID владельца на сервере. Владелец назначается доверенным способом при настройке backend. Регистрация, редактирование профиля, localStorage и параметры запросов не должны позволять назначать себе роль администратора.

- Владелец/админ: приглашения, роли, настройки, история.
- Хэд-бариста: операционное управление сменой и обязанности, согласованные владельцем; эта роль не даёт управление администраторами.
- Бариста: задачи и регистрация проблем; точная таблица прав требует согласования.

Проверки должны действовать на API/уровне базы, а не только через скрытие кнопок. Нужны тесты запрета повышения роли, доступа чужого сотрудника и повторного назначения администратора. Кнопки текущего прототипа не защищены этими правами: настоящий вход ещё не подключён.

## Смены

- Утро: 07:30–14:30 (7 часов).
- Мидл: 09:00–16:00 (7 часов).
- Вечер: 14:30–21:00 (6 часов 30 минут).

Это пересекающиеся рабочие интервалы; несколько смен могут быть открыты одновременно. В текущем прототипе это три постоянных локальных набора данных, без календаря и автоматического сброса на следующий день. Для реальной эксплуатации нужны экземпляры смен с датой, персональным составом, историей и часовым поясом кофейни.

## Инциденты и завершение

В разделе «Инциденты» можно зарегистрировать проблему и выбрать высокий приоритет. Отдельная кнопка «Срочная проблема» удалена. Главная показывает открытые срочные проблемы всех смен. Уведомления сотрудникам пока не отправляются.

После подтверждения выполненная задача и решённый инцидент становятся доступными только для чтения. Текущий прототип блокирует изменение полей, возврат к открытому состоянию и удаление завершённых записей через общий обработчик состояния. Это локальное правило поведения, а не граница безопасности: пользователь контролирует хранилище своего браузера.

Настоящее исключение для администратора необходимо реализовать на сервере только для подтверждённого аккаунта владельца. Ни пользовательская роль из localStorage, ни параметр запроса не должны предоставлять это разрешение. До подключения backend и входа исключение администратора в интерфейсе отсутствует.
